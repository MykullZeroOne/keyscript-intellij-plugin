## Where User Confusion Surfaces

Without a formal support channel, feedback arrives through these vectors:

| Signal | Location | How to read it |
|--------|----------|----------------|
| IDE Event Log | Help → Show Log | NotificationGroupManager entries from plugin |
| Support sessions (screen share) | Ad hoc | User behaviour on blank panels reveals missing empty states |
| Git issues | Repo issues tab | User-filed bugs about "nothing happens" |
| CHANGELOG requests | Internal Slack / email | Feature requests reveal unmet expectations |

The most actionable signal is the "nothing happens" bug report pattern — it almost always means a
panel failed silently (missing error state or missing auth gate).

## Reading Signals from Existing Code

Look for these patterns in the codebase to find where feedback is currently suppressed:

```kotlin
// Silent failures — catch blocks that only log, never notify the user
} catch (e: Exception) {
    log.error("Table load failed", e)
    // BAD: status label not updated, user sees stale "Loading..." text
}
```

```kotlin
// GOOD: error surfaced to the user
} catch (e: Exception) {
    log.error("Table load failed", e)
    SwingUtilities.invokeLater {
        statusLabel.text = "Error: ${e.message}"
        loadButton.isEnabled = true
    }
}
```

Run this search to find silent catch blocks:

```bash
grep -rn "catch (e: Exception)" src/main/kotlin/ | grep -v "statusLabel\|notify\|balloon"
```

Each result is a candidate for adding user-facing feedback.

## Log-Based Issue Detection

The `[ERROR]` and `[WARN]` prefixes in `ConsolePanel` are the in-app feedback channel for script
execution. They're generated by `NetworkMonitorService`. Ensure error responses from Keystone always
surface here, not just in the IDE log.

```kotlin
// NetworkMonitorService — console event emission for errors
fun logConsoleEvent(level: String, message: String) {
    val entry = ConsoleEntry(
        timestamp = System.currentTimeMillis(),
        level = level,   // "[ERROR]", "[WARN]", "[INFO]", "[LOG]"
        message = message
    )
    listeners.forEach { it.onConsoleEntry(entry) }
}

// Usage for a failed proxy request:
networkMonitor.logConsoleEvent("[ERROR]", "Proxy request failed: ${response.status} ${request.url}")
```

## Notification History as Signal

IntelliJ's notification system keeps a history in the Event Log. Use `NotificationType.WARNING` for
recoverable errors (wrong credentials) and `NotificationType.ERROR` for hard failures (proxy can't
start). Avoid overusing `ERROR` — it triggers alarm and users mute persistent offenders.

```kotlin
// AuthenticationService — existing pattern for login failure notification
NotificationGroupManager.getInstance()
    .getNotificationGroup("Keyscript")
    .createNotification(
        "Login Failed",
        "Could not authenticate: ${result.error}",
        NotificationType.WARNING   // WARNING not ERROR — user can retry
    )
    .notify(project)
```

These improvements are directly traceable to likely user confusion in the current code:

| Observation | Root Cause | Fix |
|-------------|-----------|-----|
| TableBrowser shows blank on first open for unauthenticated users | No auth check in `componentShown` | Add `session.isLoggedIn` gate |

| "Loading tables…" text persists if network is unreachable | `catch` block doesn't update status label | Update `statusLabel.text` in catch |
